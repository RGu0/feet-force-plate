# RAY-99 R10: cloud access to a local basic-report copy

Date: 2026-09-28. Status: design for review. Requirement source: Linear RAY-99 R10.

## Intent and boundary

An institution should be able to find and retrieve the same basic report that its Windows client produced after a valid four-stage test, even while authoritative cloud recomputation is not deployed. This is an explicitly labeled `LOCAL_BASIC_COPY`, not `CLOUD_COMPLETE` and not a source for cloud algorithms or clinical diagnosis. A platform hold must block this copy's listing, direct read, and export without changing the ingested session or its raw objects. The earlier R9 synthetic hold and disposition results remain historical evidence; they do not establish this R10 report behavior.

The current local path reads committed encrypted segments with the machine's `KeyProvider`, computes a `LocalAnalysisResult`, maps it to `BasicReportDocument`, and renders PDF using PySide6. The upload queue currently sends encrypted segment files and a manifest; the cloud object-store interface is write/delete only. The seed service has no production report repository, read endpoint, or analysis worker. Server-side reproduction of the local calculation would therefore first require a separate decryption/read and worker design. R10 avoids claiming that capability.

## Selected design

Use the existing local `BasicReportDocument.to_json()` and `BasicReportPdfRenderer` output. After the raw session is cloud-confirmed and any controlled identity recovery has completed, the client records an immutable report-copy handoff in the same local encrypted SQLite store. It binds the report to the immutable local session, cloud subject/consent mapping, `report_id`, version, document SHA-256 and PDF SHA-256. The upload worker serializes this handoff independently of capture and UI, uses the existing authorized transport, and resumes from SQLite after a process or network failure. A cloud confirmation must precede any local deletion; the ordinary client flow keeps the local report.

The server adds a tenant-scoped report-copy repository and private object read/write adapter. Its accept endpoint derives tenant and account from authentication, checks the server session is `INGESTED`/`VALID`, verifies the session's current subject and necessary consent binding, accepts only `BASIC_READY`/`BASIC` document version 1 and a bounded PDF, validates declared digests and session/report identity, and stores the immutable pair. Repeating the same idempotency key and digests returns the same receipt; any changed digest or binding conflicts without replacing the existing copy. A failure between object write and database commit leaves an unreferenced object for bounded cleanup, never a visible partial report. This copy is stored separately from the future authoritative cloud report version, with an explicit source marker and provenance.

The institution report-list, document-read and PDF-export endpoints derive tenant from the authenticated request, enforce institution role, locate the report-to-session binding, and check the current platform hold state on every request before returning any content. The same rule applies to direct report IDs and version IDs. They issue no public or reusable object URL, set `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`, and record a redacted access/export audit. A held session is omitted from a list and direct read/export returns a stable denial; a cross-tenant or unauthorized request cannot distinguish or retrieve another tenant's report. Requests already completed before a hold cannot be revoked, but requests starting after the committed hold cannot obtain a report from these endpoints. The server never treats an uploaded document's metric values as authoritative analysis input.

The existing hold service continues to block future cloud analysis/report publication at their invocation boundaries. R10 does not call an absent worker a live integration test. Any future worker must perform a fresh authoritative hold read immediately before each job; `CLOUD_COMPLETE` publication remains a separate acceptance gate.

## Delivery and proof

`unverified-session-hold` / PR #59 owns the migration, tenant-scoped storage and report-copy API, hold checks, access audit, and an integration test against real PostgreSQL plus the private object adapter. Create a new synthetic valid session through normal ingestion, attach a synthetic local-basic document and PDF, prove it can be listed/read/exported before hold, then apply a Platform OWNER hold and prove all three are denied, while the raw-object hashes and `INGESTED` state remain unchanged. Prove cross-tenant/role denials, digest conflict, idempotent retry, incomplete/invalid-session rejection, and `PLANNED` disposition without claiming deletion. Preserve the already verified R9 result, then use this new R10 evidence for readiness.

`windows-packaged-acceptance` / PR #52 owns the persistent client handoff, exact-head Windows package, and one real four-stage test. Confirm the same report ID/version and document/PDF digests locally and in the cloud copy; test offline, slow network, process and service restart, and identity-recovery gating without a second physical run. Its report-copy upload cannot occur while the subject mapping or new necessary consent is unresolved. Existing 24-hour/50-session/2-GiB limits still block only new tests, not this handoff.

Tests must distinguish a real report copy from a synthetic opaque raw-session payload. The synthetic R9 raw session cannot produce a legitimate report by calculation, so the R10 test report is explicitly synthetic and has no clinical meaning. No passwords, tokens, subject identity plaintext, private keys, or report content enter governance evidence. The R10 result must be labeled internal acceptance and must not imply a signed customer release.

## Alternatives considered

Running the client PDF renderer on the server would add Qt to the seed service while still lacking the client decryption key and committed-local-session reader. Uploading only client-computed features as if cloud-authoritative would contradict RAY-99's source-of-truth rule. Full server raw-data decryption, analysis and PDF generation remains the proper `CLOUD_COMPLETE` path, but its storage-read, key custody, worker and validation work is outside this R10 bridge.
