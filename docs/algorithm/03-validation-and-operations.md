# 算法验证、运行与交付说明

## 1. 可复现的分析运行

每次算法运行必须新建不可覆盖的 `AnalysisRun`。最少记录如下身份材料：

| 类别 | 必须记录 |
|---|---|
| 输入 | 会话 ID、输入模式、原始/观测文件 SHA-256、帧数、时间范围 |
| 硬件 | 设备规格、协议 profile、适配器、几何、基线和力模型版本 |
| 采集 | 阶段清单版本、部署姿态、操作员确认、质量/异常摘要 |
| 算法 | 特征管线版本、参数版本、规则集/参考数据版本 |
| 输出 | 输入合规等级、允许用途、结果摘要、生成时间 |

任何输入摘要、基线、力模型、部署姿态或算法版本变化，都必须产生新的 `AnalysisRun`。旧结果保留，可被复现但不被覆盖。

## 2. 验证层级

| 层级 | 目标 | 当前状态 |
|---|---|---|
| 协议与数组 | 串口帧、3072 点、列主序、主机时间和原始留存 | 已有真机观察与自动化回归 |
| 首版工程换算 | 空载基线和候选 `provisional_force_n` 支持开发分析 | 可用，但只限研究路径 |
| 正式物理输入 | 真实 `normal_force_n`、有效面积、时间/坐标/力验证 | 未完成 |
| 算法工程验证 | 回放一致性、质量门控、阶段/姿态转换、边界测试 | 可从首版候选力开始 |
| 产品/临床验证 | 参考范围、规则性能、可用性和前瞻性证据 | 未完成 |

从候选力提升到正式输入，至少需要覆盖重复加载/卸载迟滞、不同板面位置、温漂、坏点与逐点增益、不同设备的一致性、有效接触面积，以及与已知载荷和人体使用场景相匹配的误差边界。完成这些工作后，才可将独立验证证据对应的版本输出为 `normal_force_n`；不能通过修改现有候选字段名称完成升级。

## 3. 测试与失败处理

算法层的自动化测试至少应覆盖：

- 固定原始 fixture 经适配器后，阵列、坐标、候选力和版本摘要完全一致；
- 空载、低载、饱和、坏点、缺帧、异常到达间隔和阶段边界；
- 90° 部署变化和左右前脚语义下的 ML/AP 映射；
- 相同输入和版本重复运行得到相同特征摘要；
- `PROVISIONAL_RESEARCH` 请求正式报告时被硬拒绝；
- `VALIDATED_RELEASE` 缺少任何必需验证字段时被硬拒绝。

真机、已知载荷、人体动作和机构操作演练不能由自动测试替代。失败或不确定数据应保留原始分段、质量标记和拒绝原因，供操作员复核；不得静默删除、篡改或自动“修正”为正常结果。

## 4. 存储与通信边界

本地硬件层当前可把原始数据写为 5–10 秒的 AES-256-GCM 加密不可变分段，使用原子落盘、密文 SHA-256、SQLite 队列和恢复扫描处理电源/进程中断。上传确认后才允许按保留策略清理本地分段；本地空间达到配额时，可按当前会话数据可丢弃的业务策略停止或提示操作员核查，不能误删已确认前的数据。

当前仓库尚未实现端到端 HTTPS 上传、服务端身份验证、分段 ACK、断网重试租约或云端接收器。因此：

- 本地离线采集、加密保存、恢复和算法回放可以继续使用；
- 不能宣称已具备“采集后自动上传并由服务器确认清理”的完整通信链路；
- 将来通信实现应以上传加密原始分段/会话清单为主，服务端确认摘要和会话完整性后返回 ACK；本地仅据 ACK 更新 SQLite 状态与清理资格；
- 身份密钥的服务器注册/轮换和网络认证属于独立安全与云端工作项，不能用当前本地加密替代。

## 5. 发布检查单

首次算法开发交付应明确写为“基于 DO-P4864 首版候选力的内部分析”。交付包至少包含输入摘要、模型/基线/算法版本、质量结论、阶段与姿态记录、研究特征和限制说明。

对外筛查发布前，除完成正式物理输入验证外，还需确认端到端采集编排、上传/ACK、恢复演练、权限与审计、算法参考范围、产品安全门控和人工操作验收。任何一项未满足时，结果都必须保持内部研究或“无法正式评价”状态。
