# 种子机构 MVP License、账号、硬件与平台运维设计

**状态：** 已批准设计，待实施计划

**日期：** 2026-08-01

**适用阶段：** 不超过 10 家种子机构的第一版商业验证

**关联工作：** Linear RAY-116，并为 RAY-97、RAY-98、RAY-100 提供安全与部署前置条件

## 1. 目的与决策摘要

第一版采用服务商预配置模式。客户不搜索、新建或加入机构，也不承担机构后台管理：Platform Operations 在交付前创建机构、机构使用账号、License 和已售硬件记录，并建立四者关系。客户只需使用机构账号和一次性激活码完成首次激活、设置密码并连接已登记硬件。

本设计作出以下明确决策：

1. `tenant` 是长期稳定的数据隔离边界；机构增减账号、License、硬件或电脑都不改变历史数据归属。
2. License 不绑定电脑终端。电脑只是可替换的客户端安装环境；客户可退出后在新电脑登录。
3. License 授权机构账号使用一台已登记的实体硬件。首版默认一个 License 对应一个机构使用账号和一个硬件，但同一机构可拥有多组账号、License 和硬件，共享同一租户数据空间。
4. 服务商使用独立的 Platform IAM，不把跨租户权限塞进机构用户表，也不存在唯一的“开发者超级账号”。
5. 第一版使用单 PostgreSQL 实例和私有对象存储，通过 Repository/ObjectStore 接口保留迁移到 RDS、分区、读副本和分布式对象存储的能力。
6. 当前 `7443` 环境只作为集成验证环境；种子客户正式接入使用域名、受信任 CA 证书和标准 HTTPS 端口，不公开数据库端口。

本规格覆盖并替代现有文档中以下假设：License 绑定 `terminal_id`、由机构管理员生成激活码、客户自行搜索/创建/加入机构。其他既有数据隔离、采集、上传、分析和报告设计继续有效。

## 2. 本期范围与非目标

### 2.1 本期范围

- Platform Operations 预创建机构、机构账号、License 和硬件绑定；
- 客户首次激活、设置密码、登录、刷新会话和更换电脑；
- 6 个月或 12 个月 License，有效期可由平台配置；
- License 远程续约、暂停、恢复和吊销；
- 一台硬件同一时刻只有一个有效采集租约；
- 每日后台上传和周期性 License/策略同步；
- 机构维度的数据隔离；
- Platform IAM 多账号、多角色、跨租户运维和敏感身份受控访问；
- 客户端可配置自动锁定；
- PostgreSQL 持久化、私有对象存储、审计、备份与受控服务启动；
- 本地、API、数据库重启和阿里云种子环境的可复现验收证据。

### 2.2 本期非目标

- 客户自助创建或加入机构；
- 客户侧机构管理员后台、成员邀请或权限管理；
- License 在线购买、计费或自动续费；
- 允许一个账号同时控制多台硬件进行并发采集；
- 跨机构合并数据；
- 微服务拆分、分布式数据库或独立数据仓库；
- 向公网开放 PostgreSQL、对象存储桶或内部管理接口；
- 把回放或集成测试证据表述成真实硬件、临床或生产验证。

## 3. 角色与权限边界

### 3.1 机构侧

首版只需要“机构使用账号”。账号属于单个 `tenant`，可执行登录、采集、查看本机构历史记录、生成或导出本机构报告和后台上传。数据访问始终从认证上下文取得 `tenant_id`，不能由请求载荷自行指定。

数据模型继续保留租户角色与绑定表，使未来可以在不迁移账号数据的情况下增加机构管理员、操作员、只读人员等角色。首版不提供这些角色的客户管理界面。

### 3.2 平台侧

平台人员使用独立的 Platform IAM：

- `PLATFORM_OWNER`：管理平台角色和最高风险策略；
- `PLATFORM_OPERATIONS`：创建机构、账号、License、硬件关系，执行续约、暂停、恢复和换机/换硬件流程；
- `PLATFORM_SUPPORT`：查看必要的跨租户运营信息，处理工单；
- `PLATFORM_ENGINEER`：查看系统、任务、上传和诊断信息，不默认获得患者身份明文。

同一人员可有多个经过审计的角色绑定。平台 API 先完成平台身份授权，再为每个业务事务显式选择目标 `tenant_id`；应用账号不获得 PostgreSQL `BYPASSRLS`。

患者姓名、联系方式等身份明文不是平台角色的常驻权限。访问时必须提供目标机构、用途或工单号，获得短时授权（首版为 15 分钟），并写入不可变审计记录。具备相应角色的平台人员可查看跨租户运营数据和报告，但默认遮蔽报告中的身份字段；查看身份明文仍须取得上述短时授权。

## 4. 核心领域模型

本期以独立实体和带有效期的关系表建模，避免把动态关系写死在账号、License 或终端的一列中。

| 实体 | 责任 | 关键状态/约束 |
|---|---|---|
| `Tenant` | 机构及数据隔离边界 | 机构停用不删除历史数据 |
| `TenantAccount` | 机构使用身份 | `PENDING_ACTIVATION / ACTIVE / SUSPENDED`；只属于一个租户 |
| `License` | 商业授权、期限和功能 | `ISSUED / ACTIVE / SUSPENDED / EXPIRED / REVOKED`；6 或 12 个月可配置 |
| `HardwareDevice` | 已售实体压力硬件身份 | 序列号/硬件 ID 唯一，属于一个租户时需有有效绑定 |
| `LicenseAssignment` | License 与机构账号的历史关系 | `valid_from/valid_to/status/change_reason`；同一时刻一条有效关系 |
| `HardwareBinding` | License 与硬件的历史关系 | `valid_from/valid_to/status/change_reason`；换硬件不覆盖历史 |
| `ClientInstallation` | 可替换电脑安装上下文 | 仅用于会话、版本、诊断和风险审计，不决定 License 所有权 |
| `HardwareLease` | 防止同一硬件并发采集 | 短 TTL、心跳续租、崩溃后自动释放 |
| `PlatformIdentity/RoleBinding` | 服务商人员和权限 | 与租户账号完全分离 |
| `SensitiveAccessGrant` | 身份明文短时访问 | 目标租户、用途、到期时间和使用审计必填 |
| `AuditEvent` | 关键操作证据 | 追加写；记录操作者、对象、前后状态、原因、时间和关联 ID |

首版默认每个 License 同时只有一个有效账号分配和一个有效硬件绑定。一个 `Tenant` 可以拥有多组 License。机构从 1 台扩展到 3 台，再缩减到 2 台时，只结束相应分配/绑定并保留历史；机构数据和既有报告不删除、不迁移。

License 到期与访问令牌到期是两个概念。License 可持续 6 或 12 个月；首版访问令牌有效 15 分钟，旋转刷新令牌在持续使用时可静默续期，30 天无使用后失效，单次登录最长保持 180 天。这样不要求每日登录，同时避免把半年有效期直接变成长效访问令牌。

## 5. 交付、激活与日常使用流程

### 5.1 服务商交付前

1. Platform Operations 创建或选择机构 `Tenant`；
2. 创建处于 `PENDING_ACTIVATION` 的机构使用账号；
3. 登记已售硬件的稳定硬件 ID；
4. 签发 License，写入期限、功能、账号分配和硬件绑定；
5. 生成一次性高熵激活码，只保存其受控 HMAC/哈希和使用状态；
6. 通过独立交付渠道把机构账号和激活码交给客户。

### 5.2 客户首次激活

1. 客户输入机构账号和一次性激活码；
2. 服务端验证账号、License、租户、有效期和一次性码；
3. 客户设置新登录密码并连接硬件，客户端读取硬件 ID；
4. 服务端核对硬件与 License 的有效绑定；
5. 全部匹配后，在同一事务中保存强密码哈希、激活账号和 License、作废一次性码并签发登录会话；核对失败时不保存新密码，也不消耗激活码；
6. 不匹配、激活码已使用、硬件已被其他有效 License 占用等异常进入 Platform Operations 处理，不让客户选择或修改机构。

激活码不是登录密码，首次使用后不可再次使用。错误响应使用通俗提示且不泄露“账号是否存在”“硬件属于哪个机构”等可枚举信息；服务端对激活和登录实施速率限制、失败计数和安全审计。

### 5.3 日常登录和更换电脑

客户在任意受支持电脑上使用机构账号登录。开始采集前必须连接与 License 匹配的实体硬件并取得 `HardwareLease`。因此登录多台电脑不会获得多台硬件的并发采集能力。

更换电脑不需要重新绑定 License；新电脑登录并连接原硬件即可。硬件更换、遗失或维修由 Platform Operations 结束旧 `HardwareBinding`、创建新绑定并记录原因。

### 5.4 同机构增加或减少设备

增加设备时，Platform Operations 在同一 `Tenant` 下创建新的账号、License、硬件记录和关系。所有有效账号看到的是同一机构数据空间。减少设备时暂停、到期或结束对应 License/关系，保留机构历史数据。未来可在保持这些实体不变的前提下增加共享账号、机构角色或计费策略。

## 6. License、离线与远程控制语义

- License 的 `valid_from/valid_to` 由 Platform Operations 配置，首版提供 6 个月和 12 个月预设；
- 续约创建新的有效期版本并记录操作者、原因和前后值；
- `SUSPENDED` 阻止开始新测试，但不终止正在进行的采集、不阻止当前会话安全收尾、不阻止查看已有报告和上传已采集数据；
- `REVOKED` 是明确的永久撤销，恢复必须重新签发或建立新授权；
- `EXPIRED` 由有效期计算，不删除账号或数据；
- 客户端至少每日同步策略和 License 状态，并在在线时更频繁地轻量检查；
- 短时断网使用已签名、已缓存的 License 策略。首版沿用最长 24 小时离线宽限；超过宽限后禁止开始新测试，仍允许历史查看和待上传数据恢复；
- 服务端下发的 License 载荷签名，本地只持有验证公钥，客户端时间回拨和策略降级写入风险审计。

## 7. 客户端锁定与后台任务

机构用户可以选择“不自动锁定”或在无操作 5、15、30、60 分钟后锁定，建议默认 30 分钟。锁定仅保护界面和敏感操作，不退出后台同步、不清除待上传队列，也不要求每天重新登录。

正在采集或正在完成报告时不强制弹出锁屏；锁定请求延迟到安全点执行。解锁使用当前账号凭据，未来可增加系统生物识别或机构 SSO，但不纳入首版。

后台任务尽量每天上传数据，并通过幂等队列重试。License 暂停、界面锁定或访问令牌静默刷新不能造成已采数据丢失。

## 8. 服务与存储架构

第一版保持模块化单体，边界如下：

- `Tenant IAM`：机构账号认证、刷新会话和租户角色；
- `Platform IAM`：平台人员认证、角色和敏感访问授权；
- `Provisioning/License Service`：机构交付、激活码、License 状态和动态分配；
- `Device Service`：硬件登记、绑定、租约、心跳和客户端安装记录；
- `Upload/Reporting Services`：沿用现有租户范围上传、分析和报告能力；
- `Audit Service`：关键安全和运营事件的追加写记录；
- `Repository` 与 `ObjectStore` 接口：隔离业务逻辑与具体存储实现。

PostgreSQL 是账号、License、硬件关系、会话、索引和审计的权威数据源。原始压力矩阵和报告制品进入私有对象存储，数据库只保存不可猜测对象键、校验和、大小、状态和版本。客户端 SQLite 只保存本机缓存、待上传队列和可恢复状态，不是云端权威数据源。

所有租户业务表继续执行 RLS，唯一约束和高频索引以 `tenant_id` 为首列。Platform IAM 表不伪造 `tenant_id`；跨租户平台操作在授权后显式设置目标租户事务上下文。

## 9. API 与安全约束

API 分为两套认证域：

1. 机构 API：首次激活、登录/刷新、License 状态、硬件租约/心跳、上传、报告；
2. 平台 API：机构、账号、License、硬件和绑定管理，以及敏感访问授权。

两套令牌使用不同的受众或签名上下文，不能互换。平台管理 API 不暴露在匿名公网路径，必须执行强认证、角色检查、速率限制和审计；后续可增加 VPN、零信任接入或管理 IP 限制，不改变领域模型。

所有通信使用 TLS。密码、激活码、刷新令牌和签名私钥不得进入日志；日志只记录内部 ID、结果码和安全必要上下文。激活码和刷新令牌支持一次性使用/轮换与重放检测。对象下载使用短期签名 URL 或服务端代理，桶保持私有。

## 10. 部署基线

种子环境采用以下最低基线：

- 客户流量通过域名、受信任 CA 证书和 HTTPS 443；现有 IP + 自签名证书 + 7443 仅保留为集成验证；
- PostgreSQL 5432 只监听私网或本机，不加入公网安全组；
- migration、application、enrollment/activation 使用分离的数据库角色和最小权限；
- 密钥与口令通过权限为 `0600` 的服务环境文件注入，后续可替换为 KMS/Secret Manager；
- 服务由 systemd 或等价的受控守护进程启动，具备重启策略和健康检查；
- 健康接口不返回数据库地址、版本、堆栈或密钥状态；
- 每日数据库备份和对象清单备份，保留可验证的恢复点；
- 上线前完成一次备份恢复演练；
- 资源增长后可把 PostgreSQL 迁移到 RDS、增加读副本/分区，把对象迁移到 OSS，并把后台任务移到 worker；业务实体和 API 语义不变。

## 11. 错误处理与恢复

- 激活、登录和硬件核对失败不返回可用于枚举租户或账号的细节；
- 激活操作使用数据库事务，账号、License、一次性码和硬件关系必须全部成功或全部回滚；
- 续约、暂停、恢复、吊销和换硬件要求幂等键，重复请求不得重复变更；
- 硬件租约通过 TTL 和心跳恢复客户端崩溃，不依赖人工清锁作为正常路径；
- 服务重启后账号、License、绑定、审计和待处理上传状态必须保持；
- 上传采用内容校验和、分段幂等和最终提交，网络中断后从安全点继续；
- 审计写入失败时，高风险平台变更必须失败关闭，不允许“变更成功但无审计”。

## 12. 验收与 Linear evidence

每个完成项都必须把“实现证据”和“环境边界”一起写入 Linear。可在无硬件条件下完成并标记的证据如下：

1. **数据模型与迁移**：新数据库迁移、约束/RLS 测试、1→3→2 License/硬件关系历史测试；
2. **激活与认证**：预配置、一次性码、设置密码、登录/刷新、重放和速率限制的 API 测试；
3. **License 控制**：6/12 月、续约、暂停、恢复、吊销、24 小时离线语义和“当前测试安全收尾”的状态机测试；
4. **跨电脑与并发**：新安装登录成功、同一硬件只允许一个采集租约、TTL 恢复测试；
5. **租户隔离**：两机构同名/同外部编号数据互不可见，机构令牌不能调用平台 API，平台事务必须显式选择租户；
6. **平台权限**：多个 Platform Identity、角色矩阵、15 分钟敏感访问授权和不可变审计测试；
7. **客户端锁定**：不锁定及 5/15/30/60 分钟策略、采集中延迟锁定、锁定后后台上传继续的确定性测试；
8. **持久化与恢复**：PostgreSQL 重启、服务重启、重复请求和备份恢复演练；
9. **阿里云网络集成**：真实 TLS 请求完成激活→登录→硬件租约→心跳→上传元数据链路，记录部署版本、时间、端点、响应和测试报告；
10. **安全负向证据**：端口扫描确认 5432 不公开，匿名/错误租户/过期令牌/重放/越权请求被拒绝，健康接口不泄密。

无实体 DO-P4864 时，上述证据只能证明 License、账号、租户、持久化、网络和模拟硬件身份链路完成，不能证明真实串口采集、设备唯一身份防克隆、现场网络、操作员、临床或生产就绪。需要实体硬件的验收继续保留为独立未完成项。

Linear 完成标准：关联提交或文件、可复现命令、机器可读测试结果、关键请求/响应摘要、环境与版本、证据边界齐全后，才把对应功能标记为完成；只有方案或代码而没有运行证据时不得关闭。

## 13. 实施切片

本设计作为一个纵向 MVP，由以下顺序实现：

1. 追加数据库迁移与领域模型，保留旧迁移历史；
2. 实现独立 Platform IAM 与平台预配置 API；
3. 实现机构激活、登录/刷新、License 状态机和硬件租约；
4. 接入持久 Repository、私有 ObjectStore 和审计；
5. 接入客户端真实远程认证、后台同步和自动锁定；
6. 更新当前架构、数据库、通信、PRD 和模块文档；
7. 在本机完成无硬件测试与 evidence；
