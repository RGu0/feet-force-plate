# RAY-99 R7: controlled identity recovery and unverified-session hold

## Purpose and current state

An offline Windows screening can be locally `VALID` while its institution record number resolves to an existing cloud subject with a different UUID. RAY-99 must retain the sealed four-stage session, prevent a silent subject or consent rebind, and allow upload only after verified identity and fresh necessary-processing consent. The 2026-09-23 acceptance run exposed a gap: the terminal showed only masked identifier suffixes, yet allowed an operator to assert that the records were the same person. The operator later stated they could not make that determination. The local queue recorded `CLOUD_CONFIRMED` for 16 retained segments. That run is an unverified-identity incident, not an acceptance pass.

The current terminal composition fails closed without an independent identity verifier. The cloud already separates terminal authentication from platform OWNER/SUPPORT identity access. A platform user can obtain a purpose- and ticket-bound grant lasting at most 15 minutes and read name/contact through the audited sensitive-access boundary. Consent revocation exists, but it does not remove an `INGESTED` session or undo analysis. There is no implemented administrative hold for an already-ingested session.

## Chosen approach and boundaries

Use a server-side comparison and an opaque, one-use recovery receipt. The terminal must never receive the cloud's plaintext name or contact. Platform OWNER/SUPPORT credentials and grants must never enter the terminal client, local spool, logs, or shared evidence. The exact institution number, issuer, tenant and masked suffix are routing clues, not independent proof of personhood. Age and sex are also insufficient proof.

The comparison requires two independently sourced subject-level fields: name and contact from the original institution record, each matching a present cloud identity field under conservative canonicalization. An absent field, ambiguous contact, mismatch, revoked/expired grant, or more than the allowed audited attempts yields no receipt. Do not return which field failed. If either record lacks these fields, automated recovery remains blocked and the case goes to authorized manual review; this design does not fabricate identity values or accept a single field instead.

### Case creation and comparison

1. After an identity conflict, the authenticated terminal creates a recovery case bound to tenant, original session UUID, local and cloud subject UUIDs, the immutable upload-envelope SHA-256, the institution identifier's issuer/type, and its terminal identity. The case contains no name, contact or raw segment. Case creation is idempotent and cannot replace an existing binding.
2. The terminal presents the case reference and the need for two independent fields. A platform OWNER/SUPPORT operator uses a separate platform session and an existing short-lived sensitive-access grant with a purpose code and incident ticket. They obtain the local values from the institution's authorized original record, not from a guessed cloud value or the suffix shown on the terminal.
3. A new platform comparison operation consumes the grant for this cloud subject, reads the cloud identity inside the sensitive-access service, compares the two supplied values, and records only the case binding, compared field names, match decision, grant ID, platform actor, ticket and time. Submitted plaintext values are handled in memory under TLS; they are excluded from persistent case/receipt records, responses, diagnostics and logs. Failed attempts are bounded, audited and do not disclose per-field results.
4. Only a two-field match creates an opaque receipt bound to the case, tenant, original session, both subjects and envelope digest. The receipt expires after 15 minutes and can be consumed once. A lost response is retried idempotently against the same case and decision; it must not issue a second independent receipt.
5. The terminal retrieves the non-sensitive receipt under its own authenticated tenant/terminal context. It must validate every binding before displaying a fresh necessary-consent step. The optional research purpose remains separate and unchecked by default. The original envelope, consent and sealed segment bytes remain immutable.
6. Only after the subject or authorized representative actively completes the fresh necessary-consent step does a dedicated recovery registration operation atomically consume the receipt and create the new signed consent plus cloud session registration. It checks the same tenant, session, subjects, envelope digest, terminal and expiry server-side. The generic consent and session endpoints cannot be used to bypass this recovery binding for a session with an open recovery case. Idempotent retry returns the same registration result after a lost response. Segment transfer and manifest completion then reuse the existing durable upload queue. Once registration succeeds, a later network outage does not invalidate the registered session merely because the short receipt expires.

The local encrypted recovery authorization records the receipt/case reference, platform ticket and new consent binding without storing identity values. The server's audit record is authoritative for grant use, matching and receipt consumption. The UI must identify the source of each comparison outcome and never ask the terminal operator to attest “same person” from a masked number alone.

### Unverified-session hold and disposition

The 2026-09-23 session is already `INGESTED`; the new receipt flow must not retroactively approve its checkbox attestation. Introduce an audited administrative hold keyed by tenant and session, without rewriting immutable ingestion status or deleting object-store data. A platform OWNER/SUPPORT operator can create the hold with an incident ticket and reason. Report access/publication and new analysis work must check an active hold. A hold cannot undo processing already completed; the audit must state that limit. Its release requires a separately recorded authorized disposition, not merely a later identity match.

The privacy/service operator then reviews the platform identity under a short-lived grant, the original institution record, the replacement consent, the session status and any downstream report/analysis. They record a decision to retain under a valid basis or to revoke the replacement consent and initiate governed restriction/disposition. Existing consent revocation changes the consent record only; accepted raw data must follow the retention/disposition controls and cannot be deleted by an upload retry or terminal action. A mismatch or inability to verify keeps the hold. No automated action treats a new consent as retroactive authorization for prior processing.

Until the hold operation is deployed and executed, the incident remains open; closing the desktop app only stops that process. No acceptance, merge, release or “resolved” status may cite the existing `CLOUD_CONFIRMED` flag as identity proof.

## Failure behavior and security constraints

- Terminal and platform tokens stay in their own clients and audiences. The terminal cannot call platform identity endpoints; platform grants cannot be entered into the terminal.
- Case, receipt and hold operations are tenant-scoped, permission-checked, audited and protected against replay/cross-case substitution. The receipt is an opaque server-side reference, not a bearer permission by itself.
- Missing local/cloud identity fields, comparison disagreement, unauthorized platform role, expired grant/receipt, network failure, or stale case binding fail closed. Local raw data and prior audit remain readable under existing rules and are not automatically resent.
- API errors, support diagnostics, shared evidence and UI screenshots contain no plaintext identity, full record number, token, signature or raw data. Comparison attempts return one generic non-match result to limit identity probing.
- Cloud migrations add tenant-first keys and row-level policies for cases, receipts and holds. The upload and reporting boundaries check the hold using the same tenant context.
